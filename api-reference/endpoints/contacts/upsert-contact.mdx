Creates a new contact in your CRM, or updates an existing one if a contact with the same `email`, `linkedinUrl`, or `linkedinUrlSalesNav` already exists (upsert).

On update, the `updateStrategy` query parameter decides what the existing record keeps (see below). By default, sent values replace stored ones and empty values are ignored.

<SnippetObjectReference objectName="Contact" objectPath="contact" />

## Upsert matching

At least one identifier is required:

| Identifier | Description |
|------------|-------------|
| `contactId` | Existing contact ID — updates a specific contact directly, bypassing email/LinkedIn matching |
| `email` | Primary email address — used as the main unique key |
| `linkedinUrl` | LinkedIn profile URL — used as an alternative unique key |
| `linkedinUrlSalesNav` | LinkedIn Sales Navigator profile URL — used as an alternative unique key |

If a contact with the same `email`, `linkedinUrl`, or `linkedinUrlSalesNav` already exists, the endpoint updates it instead of creating a duplicate.

Creating a contact requires the "Create contacts" permission on the API key's user, otherwise the request fails with `403 CONTACT_CREATE_NOT_ALLOWED` and nothing is written. Updating an existing contact does not require it.

When `contactId` is provided, the contact is matched by its ID directly — `email` and `linkedinUrl` are not required and are not used for matching (they are stored as data if provided).

<Warning>
`contactId` can only be used to **update** an existing contact. It cannot be used to create a new contact — use `email` or `linkedinUrl` for creation.
</Warning>

## Update strategy

The `updateStrategy` query parameter decides what an existing contact keeps:

| Value | Stored value | Empty string sent |
|-------|--------------|-------------------|
| `overwriteIgnoreEmpty` (default) | Replaced | Ignored |
| `overwrite` | Replaced | Cleared |
| `fillEmptyOnly` | Kept | Ignored |

`null` and absent keys never touch a field. Identifiers (`email`, `linkedinUrl`, `linkedinUrlSalesNav`) are never cleared. Under `fillEmptyOnly`, the company link, the owner and the status are kept when set and filled when missing. A new contact receives every value sent. Any other value answers `400 INVALID_UPDATE_STRATEGY`.

```bash
curl -X POST "https://api.lemlist.com/api/contacts?updateStrategy=fillEmptyOnly" \
  -u ":YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email": "john@example.com", "jobTitle": "Founder", "phone": "+33600000000"}'
```

Kept values are reported: `warnings` carries a `FIELDS_KEPT` entry with the field names in `params.fields`. It appears under `fillEmptyOnly` on a stored value, and under the default when an empty string is ignored on a filled field, never for an identical value.

```json
{
  "success": true,
  "data": { "_id": "ctc_2aB3cD4eF5gH6iJ7k", "jobTitle": "CEO", "phone": "+33600000000", "created": false, "updated": true, "companyLinked": false },
  "warnings": [
    { "code": "FIELDS_KEPT", "message": "Fields kept: the record already holds a different value, left unchanged by the update strategy", "params": { "fields": ["jobTitle"] } }
  ]
}
```

## Linking to a company

You can link the contact to a company that already exists in your lemlist CRM using one of the following fields (in order of priority):

| Field | Description |
|-------|-------------|
| `companyId` | Direct company ID — takes priority over the others |
| `companyDomain` | Company domain (e.g. `lemlist.com`) — used if `companyId` is not provided |
| `companyLinkedinUrl` | Company LinkedIn URL — used as a last resort |

When a company is successfully linked, the response includes `companyLinked: true` and the `companyId`.

## Linking to a CRM record

Send `crmId` with the id of a record in your connected CRM to link the contact to that record. lemlist links it without searching the CRM, then runs a first sync that follows your field mapping (the CRM wins conflicts by default).

<Warning>
`crmId` is in closed beta. Unless the CRM ID remap beta is enabled for your team, it is refused like any unknown field, with `400 INVALID_FIELD`. It also requires an **admin** API key.
</Warning>

| CRM | Accepted id |
|-----|-------------|
| HubSpot, Pipedrive, Zoho | Numeric record id. Send a Zoho id as a string: its 19 digits are too long for a JSON number. |
| Attio | Record id (UUID) |
| Salesforce | Contact (`003…`) or Lead (`00Q…`) id, 15 or 18 characters. A 15-character id is stored as 18. |

What happens depends on the contact and on who already holds the id:

| Situation | Result |
|-----------|--------|
| New contact, the id is linked to no lemlist contact | The contact is created already linked to that record (`201`). |
| Existing contact, named by `contactId` or found by its email or LinkedIn URL | Its link moves to that record (`200`). The previous CRM record stops being synced: updates queued for it are cancelled. When your mapping includes the "synced with lemlist" field, it is set to false there; when it includes the Lemlist Contact ID, that field is cleared there. |
| The id is already linked to a lemlist contact, and at least one of the body's `email` (its primary email), `linkedinUrl` or `linkedinUrlSalesNav` is that contact's | The `crmId` finds the contact and that identifier confirms it: the body updates it (`200`) and its link stays as it is. The body's other identifiers are written to the contact, unless they already belong to another contact: `409 CONTACT_IDENTIFIER_CONFLICT`. Sending the same payload twice is safe. |
| The id is already linked to a lemlist contact, and none of the body's identifiers is that contact's | Refused, nothing written: `409 CRM_ID_ALREADY_LINKED`, `error.conflictingRecord` names that contact. Another of its email addresses is not enough: only its primary email confirms it. |

The `crmSync` block of the response shows the link the contact ends up with.

```bash
curl -X POST "https://api.lemlist.com/api/contacts" \
  -u ":YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email": "john@example.com", "firstName": "John", "crmId": "123456789"}'
```

Every check runs before anything is written, so a refused call leaves the contact as it was:

| Status | Code | When |
|--------|------|------|
| `400` | `INVALID_CRM_ID` | The id does not have the format of your CRM, or points to another kind of record (a Salesforce Account id for a contact). |
| `400` | `NO_CRM_CONNECTED` | Your team has no CRM connected. |
| `403` | `CRM_ID_UPDATE_NOT_ALLOWED` | The API key does not belong to a team admin. |
| `409` | `CRM_ID_ALREADY_LINKED` | Another lemlist contact holds the id (see above); `error.conflictingRecord` names it. |
| `422` | `CRM_RECORD_NOT_FOUND` | No record with this id exists in the CRM, or it was deleted. |
| `422` | `CRM_RECORD_MERGED` | The record was merged into another one; `error.survivorId` is the id to send. |
| `422` | `CRM_RECORD_CONVERTED` | The Salesforce Lead was converted; `error.convertedContactId` is the Contact id to send. |
| `422` | `CRM_ID_LEADS_NOT_SYNCED` | A Salesforce Lead id, while your team does not sync Leads. |
| `503` | `CRM_RECORD_UNREACHABLE` | The CRM could not be reached to check the record. Retry. |

```json
{
  "success": false,
  "error": {
    "code": "CRM_ID_ALREADY_LINKED",
    "message": "This CRM id is already used by another lemlist record",
    "conflictingRecord": { "contactId": "ctc_A1B2C3D4E5F6G7H8i", "email": "jane@example.com", "name": "Jane Smith" }
  }
}
```

A Salesforce Lead id sent with the email of a contact already linked to the Contact of the same person, without `contactId`, keeps the existing link: the response is `200` with a `CRM_ID_NOT_APPLIED` entry in `warnings`. Send the `contactId` to move the link.

## Owner assignment

You can assign an owner to the contact using the `contactOwner` field. Accepted formats:

| Format | Example |
|--------|---------|
| User ID | `usr_2aB3cD4eF5gH6iJ7k` |
| Team member email | `john@yourcompany.com` |

<Note>
If the provided value does not match a team member (invalid format, unknown email, or unknown user ID), the contact is still written and the response carries an `OWNER_NOT_FOUND` or `INVALID_OWNER_FORMAT` entry in `warnings`. On creation, the contact defaults to the API key owner; on update, the current owner is unchanged.
</Note>

On an existing contact, `updateStrategy` decides the owner:

| Strategy | Current owner set | No current owner |
|----------|-------------------|------------------|
| `overwriteIgnoreEmpty` (default) and `overwrite` | Replaced by `contactOwner` | Set to `contactOwner` |
| `fillEmptyOnly` | Kept, reported as `ownerId` under `warnings` (`FIELDS_KEPT`) | Set to `contactOwner` |

Without `contactOwner`, the owner is never touched.
